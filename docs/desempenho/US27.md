# US27 — Desempenho com cinquenta usuários simultâneos

Requisito transversal das consultas públicas (diagrama de componentes: Frontend → rotas
Flask → QueryService → Repository → MySQL). Metas: **p95 ≤ 2 s e p99 ≤ 5 s**, sem erros.

## T01 — Cenário reproduzível

Comando (MySQL local isolado; a URL vem do ambiente, nunca do repositório):

```bash
pip install -r requirements-medicao.txt
US27_CARGA_MYSQL_URL=mysql+pymysql://root:***@127.0.0.1:3306/us27_carga \
  python -m tests.carga.cenario --rotulo <nome>
```

| Item | Como é feito |
|---|---|
| Servidor | waitress (WSGI de produção), processo separado, 16 threads. O servidor de desenvolvimento não é referência; `app.test_client()` fica só nos testes funcionais |
| Banco | MySQL local isolado (só host local e base `us27_carga*`), com **todas as migrações publicadas** aplicadas pelo Alembic. Nunca a Aiven |
| Massa | [`tests/carga/massa.py`](../../tests/carga/massa.py), semente fixa, marcada como sintética. 12 meses (01/11/2025–01/11/2026): 20 linhas × 2 sentidos com CUMPRIMENTO e PONTUALIDADE a cada 15 min; 4 linhas com 3 paradas e os 5 indicadores por parada; 1,05 milhão de ciclos de coleta (um a cada 30 s), que o /series também lê |
| Usuários | 50 threads, cada uma com IP próprio atrás de um proxy confiável (`X-Forwarded-For`, como em produção), pausa de 1,2–2,2 s, abaixo do limite de 60/min por IP |
| Consultas | Iguais às do painel (`js/series/modelo.mjs`): `/series` com linha, sentido, tipo, inicio, fim, page e `page_size=50`, períodos de 1, 7, 30, 90, 180 e 365 dias. 80% /series (25% por parada, 20% páginas 2–20) e 20% `/indicadores` (até 31 dias) |
| Duração | 20 s de aquecimento (relatados à parte, não descartados) + 180 s medidos |
| Registro | versão do sistema (commit e branch), versões do servidor, banco e pacotes, volume, duração, erros por status, conexões do MySQL (atuais e máximo), cache (a aplicação não tem cache; acerto do buffer pool InnoDB), CPU e memória da API, do MySQL e do cliente, tempo em SQL × Python × fila por requisição (`Server-Timing`, de [`tests/carga/instrumentado.py`](../../tests/carga/instrumentado.py)) e as instruções SQL mais caras (`performance_schema`) |

Erros nunca contam como respostas rápidas: o relatório separa o número de erros e mostra os
percentis com cada erro valendo +∞.

## T02 — Medição antes da otimização ([US27-antes.json](US27-antes.json))

Mesma massa (7.008.000 indicadores, 1,05 milhão de ciclos de coleta, 8,9 GB de dados e
índices), migrações até `us28_0029`, 50 usuários, MySQL 8.0.46 com buffer pool padrão de 128 MB.

| Medida | Resultado |
|---|---|
| Consultas medidas | 288, **todas** com timeout de 30 s no cliente |
| p95 / p99 | 30.030 ms / 30.031 ms (+∞ contando erros) |
| Conexões do MySQL | até 67, 36 consultas rodando ao mesmo tempo em média |
| Consultas lentas | 116; 6,75 milhões de leituras de disco |

Instruções mais caras (`performance_schema`):

1. `MIN(periodo_inicio), MAX(periodo_fim)` da série: 17,5 s em média, até 50,7 s; 3,7 milhões
   de linhas examinadas em 107 execuções. Não havia índice que cobrisse
   `(linha, sentido, indicador, parada, trecho)` com as datas.
2. `COUNT(*)` da página: lia a série inteira com todas as colunas.
3. A janela `MAX(periodo_fim) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)`
   que marca a "observação anterior" de cada ponto: no MySQL esse quadro é **quadrático**.
   Leva minutos para os 35 mil pontos de um ano de uma série.

O JSON registra `FALHA_DO_TESTE` porque foi gerado antes de a classificação separar "amostra
pequena porque o sistema travou" de "amostra pequena porque o ensaio falhou". Pela regra
atual (`classificar`, T04) o mesmo resultado é **`FALHA_DO_REQUISITO`**: 288 timeouts, p95 e
p99 acima das metas. O arquivo foi mantido como gerado.

## T03 — Otimização

Tudo em [app/indicadores/series.py](../../app/indicadores/series.py),
[app/indicadores/service.py](../../app/indicadores/service.py) e na migração
[us27_0030](../../migrations/versions/us27_0030_indice_series_cobertura.py). O contrato das
respostas não muda.

1. **Índice de cobertura** `ix_indicadores_serie_cobertura` (`linha_codigo, sentido,
   indicador, parada_codigo, trecho_id, periodo_inicio, periodo_fim, unidade`). MIN/MAX,
   contagem e paginação passam a ler só o índice. As colunas de parada e trecho vêm **antes**
   das datas, porque o painel sempre filtra por elas (`IS NULL` ou valor). Com as datas antes,
   a consulta por parada varria o intervalo inteiro.
2. **Página antes das colunas largas** (`/series`): ordena e pagina só pelas colunas do índice
   e depois busca as linhas completas da página por `id`.
3. **"Anterior" e "última" só para a página**, sem função de janela. Para cada série da página:
   - o maior `periodo_fim` antes do primeiro ponto (uma consulta com `MAX`, coberta pelo índice);
   - o máximo corrente entre o primeiro e o último ponto da página;
   - o último ponto da série (`ORDER BY ... DESC LIMIT 1`).

   O resultado é idêntico ao da janela, inclusive com empates de `periodo_inicio`.
4. **`/indicadores` em dois passos**: ids ordenados e paginados primeiro; linhas completas por
   `id IN (...)`. Antes, o MySQL ordenava linhas inteiras (até 1.000 por página) em disco.
5. **`max_execution_time` por sessão** igual ao `read_timeout` da conexão. Uma consulta
   abandonada pelo cliente agora é encerrada no servidor. Antes, consultas órfãs de 27 min
   seguravam bloqueio de metadados e impediam a migração.

**Equivalência:**
[tests/indicadores/test_series_us27_t03.py](../../tests/indicadores/test_series_us27_t03.py)
mantém uma cópia da implementação antiga e compara as respostas:
- 12 casos;
- todas as páginas com tamanhos 7, 13 e 50;
- empates;
- `/indicadores` contra a versão antiga.

Com um usuário, a série de 12 meses caiu de minutos para 52–164 ms.

## Medição depois ([US27-depois.json](US27-depois.json)) — **APROVADO**

Mesma massa, mesmo cenário, mesmo buffer pool de 128 MB, migrações até `us27_0030`.

| Medida | Antes | Depois |
|---|---|---|
| Consultas medidas (180 s) | 288 | 4.979 |
| Erros | 288 timeouts | 0 |
| p50 | 30.017 ms | 87 ms |
| **p95** (meta 2.000 ms) | 30.030 ms | **198 ms** |
| **p99** (meta 5.000 ms) | 30.031 ms | **566 ms** |
| Máximo | 30.032 ms | 1.933 ms |
| Consultas lentas no MySQL | 116 | 0 |
| Leituras de disco | 6,75 milhões | 1,71 milhão |
| Conexões em uso (média / máx.) | 36 / 67 | 7,6 / 17 |

Decomposição do p95 (`Server-Timing`): SQL 167 ms, Python e JSON 26 ms, fila e rede 19 ms.

Por rota:

| Rota | Consultas | p95 | p99 |
|---|---|---|---|
| `/series` | 4.000 | 187 ms | 268 ms |
| `/indicadores` | 979 | 552 ms | 992 ms |

Por período (dias): todos com p95 entre 121 ms (1 e 30 dias) e 269 ms (7 dias).

**Recursos:** a API usou 33% de CPU em média (máx. 59%) e 152 MB. O MySQL usou 106% (1 núcleo)
e 370 MB.

**Riscos que continuam:**
- **Dados frios.** As consultas mais lentas são `/indicadores` com 100 linhas de novembro e
  dezembro de 2025: até 1,9 s, quase todo em disco. O buffer pool de 128 MB acerta 92%; em
  produção, um buffer pool maior reduz isso.
- **`COUNT(*)` da paginação.** É a instrução mais executada (5.525 vezes, média de 23 ms, até
  1,1 s). Se o volume crescer muito além de um ano, é a próxima a revisar.

## T04 — Verificação a cada versão

O mesmo comando do T01, com o rótulo da versão:

```bash
US27_CARGA_MYSQL_URL=mysql+pymysql://root:***@127.0.0.1:3306/us27_carga \
  python -m tests.carga.cenario --rotulo v<versão>
```

- A massa é reaproveitada se já estiver na base (`massa.reaproveitada`).
- As migrações pendentes da versão são aplicadas antes da carga.
- O relatório vai para `docs/desempenho/US27-v<versão>.json` com o commit e a branch medidos.

O código de saída separa os dois tipos de falha, para uso em pipeline:

| Saída | Resultado | Quando |
|---|---|---|
| 0 | `APROVADO` | p95 ≤ 2 s, p99 ≤ 5 s e nenhuma resposta de erro |
| 1 | `FALHA_DO_REQUISITO` | metas não atingidas, ou 5xx, timeout ou conexão recusada. Também quando a amostra ficou pequena porque o próprio sistema travou |
| 2 | `FALHA_DO_TESTE` | o ensaio não mediu o que promete: base, migração ou servidor fora do ar antes da carga; menos de 500 consultas sem erro do sistema; 429 por cota mal dimensionada; menos de 50 usuários ativos; cliente de carga saturado |

A classificação tem testes próprios em
[tests/carga/test_cenario_us27.py](../../tests/carga/test_cenario_us27.py), que não usam banco.
