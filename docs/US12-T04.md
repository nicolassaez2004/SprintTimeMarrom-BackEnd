# US12-T04 — Comprovar a reprodução de um mês de indicadores

**Situação: rotina implementada e testada; aceite integral pendente.** Nenhum
mês real foi comprovado: a base compartilhada não tem indicadores publicados
nem viagens reconstruídas (ver Evidências).

## Rotina

`app/indicadores/reproducao.py` (`ReproducaoIndicadores`):

1. **Seleção** — mês civil em `America/Sao_Paulo` (`[início, fim)` em UTC);
   indicadores publicados com `periodo_inicio >= início` e `periodo_fim <= fim`.
2. **Completude** — mês encerrado, brutos em todos os dias e ao menos um
   indicador publicado; caso contrário o veredito é `INCONCLUSIVO`.
3. **Versões fixadas** — base (revisão Alembic + id máximo e SHA-256 dos brutos
   do mês), código (commit git, `-dirty` se houver alterações), regra e versões
   dos algoritmos (`cumprimento-1.1`, `pontualidade-1.0`, `frequencia-1.0`). Cada indicador é
   recalculado com as versões **gravadas nele** (GTFS, correspondência,
   reconstrução); se `versao_calculo` publicado difere do código atual, o item é
   `VERSAO_INCOMPATIVEL` e não é recalculado. As capturas de programação não são
   repassadas ao cálculo: se a captura vigente hoje difere da gravada, o item é
   `VERSAO_INCOMPATIVEL` ("programação substituída"). `--versao-regra` precisa
   ser igual às versões dos algoritmos do código, senão a execução é recusada.
4. **Base pela US12-T03** — com `--reprocessar-brutos`, cria/reusa o manifesto
   de `criar_execucao_reprocessamento` (snapshot `bruto_id_maximo`) e o executa;
   confere tratados × brutos do snapshot. Grava só em `execucoes_processamento`
   e `resultados_reprocessamento`.
5. **Recálculo sem gravação** — `calcular_indicador_cumprimento` (US14),
   `calcular_indicador_pontualidade` (US16) e `calcular_frequencias` (US15,
   um conjunto por linha/sentido/data, com a lacuna gravada em
   `versao_estimativa` e o relógio do relatório): as mesmas funções usadas na
   publicação, separadas do upsert (`gravar_indicador`). Nenhum cálculo foi
   duplicado. Frequência publicada com coleta ainda pendente aparece como
   divergência, porque não era o valor final.
6. **Comparação** — chave do resultado, versão do conjunto, indicador, unidade,
   linha/sentido/parada/trecho, período, versões, contagens, qualidade e valor.
   Estados: `IGUAL`, `IGUAL_COM_TOLERANCIA`, `DIVERGENTE`, `VERSAO_INCOMPATIVEL`,
   `DADOS_INSUFICIENTES`, `NAO_SUPORTADO`, `ERRO_RECALCULO`. NULL só é igual a
   NULL.
7. **Preservação** — hash de brutos e publicados antes/depois; a sessão não
   pode ter objetos pendentes; a segunda leitura relê a base (`expire_all`).
   Indicadores com janela na virada do mês ficam fora da comparação e tornam a
   completude incompleta (`INCONCLUSIVO`). Vereditos: `REPRODUZIDO`, `NAO_REPRODUZIDO`,
   `INCONCLUSIVO`.

### Tolerância — decisão do PO

Não há tolerância acordada. O padrão é **igualdade exata** (os valores são
arredondados a 0,01 antes de publicar, então o recálculo determinístico é
bit a bit igual). `--tolerancia X` aplica tolerância absoluta somente ao valor
e é reportada separadamente (`IGUAL_COM_TOLERANCIA`); contagens, períodos e
versões são sempre exatos. **Pendente:** o PO decidir se aceita só igualdade
exata ou definir a tolerância.

### Como executar

```bash
# somente leitura (sessão MySQL READ ONLY); código de saída 0/1/2
python -m app.indicadores.reproducao --mes 2026-11 --saida relatorio.json
# fixar a base pelo manifesto US12-T03 (grava execucoes_processamento:
# NÃO usar na Aiven compartilhada)
python -m app.indicadores.reproducao --mes 2026-11 --reprocessar-brutos
```

Opções: `--versao-base` (padrão: revisão Alembic), `--versao-codigo` (padrão:
commit git), `--versao-regra`, `--tolerancia`.

## Pendências para o aceite integral

1. Aplicar na base as migrações de `viagens_observadas`/`indicadores_operacionais`
   (dono da base; não executado aqui).
2. **US14-T01C não integrada:** nenhuma rotina reconstrói `ViagemObservada` a
   partir dos brutos. O recálculo parte das viagens reconstruídas, não dos
   brutos; o critério da US12 ("recalcular um mês a partir dos brutos") exige
   essa cadeia. Ao integrá-la, ativar `RECONSTRUCAO_A_PARTIR_DOS_BRUTOS`.
3. Coletar um mês completo real, programação (US04) e publicar seus
   indicadores com versões registradas.
4. Decisão do PO sobre a tolerância.
5. Executar a rotina nesse mês e anexar o relatório. Até lá, **US12-T04 não
   deve ir para Pronto**.

Observação: `IndicadorOperacional` não guarda o commit do código; a versão de
código é fixada no relatório, e a comparação usa `versao_calculo`.
