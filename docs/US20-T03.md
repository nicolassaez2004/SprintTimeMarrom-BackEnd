# US20-T03 — Publicar uma versão consistente dos resultados recalculados

Completa a T02C. Usa a mesma `ExecucaoProcessamento` (diagrama de classes), o mesmo
worker (`python -m app.jobs`) e a mesma preservação por versão da US25. Não cria
tabela, coluna nem migração.

## O que muda

| Arquivo | Mudança |
|---|---|
| [app/indicadores/agenda.py](../app/indicadores/agenda.py) | `RECALCULO_INDICADOR` entra em `TIPOS_PUBLICACAO`: um recálculo PRONTO passa a ser a versão vigente (`versao_dados`) |
| [app/reprocessamento/execucao.py](../app/reprocessamento/execucao.py) | `preservar_publicacao` (antes do commit), `invalidar_caches` (depois do commit), `executor_recalculo` (worker completo) |
| [app/jobs/executor.py](../app/jobs/executor.py) | Etapas opcionais `preservar(job_id)` (após `concluir`, antes do commit) e `apos_confirmar(job_id)` (após o commit; falha só é registrada) |
| [app/jobs/\_\_main\_\_.py](../app/jobs/__main__.py) | O worker usa `executor_recalculo` |
| [app/exportacoes/csv.py](../app/exportacoes/csv.py) | Recibo do conjunto preservado guarda snapshot dos brutos e versões de base/regra/código; o CSV diário vencido por um recálculo posterior deixa de ser servido |
| [docs/openapi.yaml](openapi.yaml), [docs/US25-T01.md](US25-T01.md) | `versao_dados.tipo` aceita `RECALCULO_INDICADOR` |

## Ordem da publicação (uma transação)

1. `publicar_pedido` grava os resultados (upsert por `chave_resultado`) e remove,
   no escopo do pedido, o que o conjunto novo não reproduz.
2. `JobService.concluir` marca PRONTO e `finalizada_em` (sem commit).
3. `preservar_publicacao` grava o arquivo da versão (US25), com versões de base,
   regra, código e snapshot dos brutos. Falha aqui → rollback e ERRO.
4. **Commit.** Só agora `versao_vigente()` passa a apontar o pedido. Como a API lê
   `versao_dados` e os dados na mesma transação, o painel vê o conjunto antigo
   **ou** o novo, nunca um parcial.
5. `invalidar_caches`: regera o CSV diário consolidado (US10) de cada dia de São
   Paulo tocado pelo recálculo. Mesmo antes disso, o arquivo antigo já não é
   servido (`_recalculado_depois`); se a regeração falhar, o download responde 404
   até a próxima tentativa, nunca o valor antigo. Respostas de `/series` e
   `/indicadores` já saem com `Cache-Control: no-store`.

A versão anterior continua exportável por `versao_dados` (arquivo imutável).

## Verificação

`tests/indicadores/test_publicacao_versionada_us20_t03.py` (SQLite em arquivo,
sessão e conexão próprias por leitor):

- leitor durante a transação aberta vê (versão antiga, 100%); depois do commit,
  (versão do recálculo, 0%);
- rollback (falha ao preservar) mantém conjunto e versão antigos; a versão do pedido
  responde 404;
- leitor em outra thread durante todo o recálculo: só (antiga, 100%) ou (nova, 0%),
  e nunca volta à antiga depois de ver a nova;
- versões antiga e nova reproduzíveis pela exportação;
- CSV diário vencido não é servido e é regerado; falha na regeração não desfaz a publicação.

```bash
DATABASE_URL=sqlite:// TEST_DATABASE_URL= SPTRANS_TOKEN= MYSQL_SSL_CA= \
  python -m pytest -q tests/indicadores/test_publicacao_versionada_us20_t03.py
```

## Limites

- Leitores concorrentes comprovados em SQLite. No MySQL 8 (InnoDB) o mesmo código
  depende do isolamento padrão, que não expõe linhas não confirmadas; não houve
  MySQL 8 disponível para repetir o ensaio.
- No teste, o limite por IP (US11-T02) foi desligado: ele grava a cada consulta e,
  no SQLite, disputaria o bloqueio do arquivo com o worker.
- Recálculos PRONTO anteriores a esta tarefa não têm arquivo preservado; uma
  exportação por versão que dependa deles responde 410.
- O frontend mostra o tipo `RECALCULO_INDICADOR` pelo nome técnico (sem rótulo
  próprio em `painel-exportacao.mjs`).
