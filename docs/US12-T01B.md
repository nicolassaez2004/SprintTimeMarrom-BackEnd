# US12-T01B — Migrações de dados brutos e tratados

Implementado na branch `US12-T01B`, em 18/11/2026. Aguardando commit e revisão de outro integrante.

## Modelo e responsabilidade

O coletor já persiste `ExecucaoColeta` e `RegistroBrutoGPS` por meio das migrações 0001/0002. A origem continua na tabela `registros_gps`; não foi criada uma segunda tabela de brutos e não foram renomeadas tabelas usadas pelo coletor.

A revisão 0004 acrescenta `ObservacaoTratada` / `observacoes_tratadas`, conforme o diagrama de classes:

| Campo | Papel |
| --- | --- |
| id | Identificador UUID textual da observação. |
| bruto_id | FK obrigatória para registros_gps.id e UNIQUE: cada tratado tem um bruto; cada bruto tem zero ou um tratado. |
| valida | Resultado booleano do tratamento, obrigatório. |
| motivo_invalidez | Motivo opcional, separado do payload original. |
| versao_correspondencia | Versão da regra/correspondência aplicada, obrigatória e não vazia. Não representa a versão do arquivo GTFS. |
| versao_gtfs_id | FK opcional para versoes_gtfs.id: permite correspondência ainda não resolvida. |

FKs usam RESTRICT para impedir apagar uma origem ou versão GTFS ainda referenciada. Não há cascata do tratado para o bruto. A migração somente cria a tabela e seu índice; não executa UPDATE nos payloads existentes. Campos tipados do bruto, como latitude, podem estar NULL para valores inválidos, enquanto o objeto de origem permanece em `payload`.

O JSON guarda o objeto recebido conforme a política do coletor existente; não promete preservar byte a byte a representação textual HTTP. O tratamento escreve na entidade separada. Isso não torna a tabela bruta protegida contra SQL arbitrário feito diretamente por um usuário com permissão de UPDATE.

Conforme o diagrama de componentes, `MatchingService` poderá produzir esses tratados e a camada de persistência armazenará as entidades. Esta tarefa entrega os modelos e o esquema, sem iniciar processamento nem criar rotas de tratamento. Não há SQL ou acesso ao banco no Frontend.

## Limites de escopo

- Linha e viagem são vínculos opcionais no diagrama conceitual; suas FKs serão acrescentadas quando as respectivas entidades forem implementadas. Não foram criadas tabelas vazias substitutas nem colunas textuais fingindo ser FKs.
- `IndicadorOperacional` e suas relações entram nas histórias de indicadores (a partir de US14), conforme “demais tabelas entram nas suas histórias”. Não foi antecipado cálculo de indicadores nesta tarefa.
- A tabela nova usa InnoDB e herda charset/collation da base, assim como `versoes_gtfs` na 0003. Isso evita incompatibilidade nas FKs VARCHAR. A base preparada pela US12-T01A usa utf8mb4; os testes confirmaram esse charset.
- Downgrade é bloqueado porque apagaria dados tratados, seguindo a política já usada nas migrações anteriores. Não usar `db.create_all()` para atualizar bases existentes.

## Verificações executadas

1. Suíte padrão: **78 testes aprovados, 3 ignorados, 14 subtestes aprovados**. Dois ignorados são testes MySQL opt-in; o outro já existia.
2. Integração opt-in em duas bases MySQL 8.0.46 locais descartáveis: **2 testes aprovados**. Uma iniciou vazia e recebeu toda a cadeia; a outra recebeu histórico na 0003 antes da 0004. O payload original foi preservado. As bases descartáveis foram removidas ao final.
3. Conferidos UNIQUE do bruto, FKs para bruto/GTFS, rejeição de órfão, impedimento de exclusão de origem referenciada, versão de correspondência não vazia, atualização de tratado sem alterar payload, InnoDB e utf8mb4.
4. `flask db check`: sem diferença entre modelos e esquema migrado.
5. `git diff --check`: aprovado.

Os testes opt-in são `tests/test_migracoes_us12_mysql.py`. Exigem duas URLs em `US12_MYSQL_TEST_URL_VAZIO` e `US12_MYSQL_TEST_URL_HISTORICO`, apontando a bases **vazias**, descartáveis, com prefixo `us12_verificacao_`. Não usam `TEST_DATABASE_URL` do time e recusam bases com outro nome. O executor é responsável por provisionar/remover essas bases e manter as URLs fora do Git.
