# US32 — backup e recuperação

Responsável: Matheus. Criada: 17/11/2026. Iniciada: 20/11/2026.

## O que foi implementado

BackupService fica em `app/operacao/`; a leitura/escrita SQL em
`app/repositories/recuperacao.py`. São comandos internos, executados pelo
agendador fora do Flask, conforme o diagrama de componentes. As entidades
existentes (RegistroBrutoGPS, suas relações e ArquivoArmazenado) são
preservadas; nenhuma tabela de domínio foi duplicada.

O conjunto contém esquema MySQL original, todas as tabelas da base de
`DATABASE_URL`, revisão Alembic, dados, contagens e hashes por tabela;
ZIPs GTFS, JSONs oficiais e PDFs referenciados no mesmo snapshot;
limite municipal, quando configurado; configuração dos caminhos sem senhas.
Parquets derivados podem ser reconstruídos dos brutos. Backups da base
de desenvolvimento não são apresentados como backup de outra base.

O pacote usa o formato **time-marrom-mysql-jsonl-v2**: `esquema.json` contém
os CREATE TABLE originais, e `dados/*.jsonl` contém linhas com tipos
preservados (incluindo binários, geometrias, decimais e microssegundos).
É um dump lógico próprio, restaurado pelo comando abaixo. **Não importar
JSONL no Workbench como se fosse SQL.**

Foi avaliado `mysqldump --single-transaction --quick --no-tablespaces
--set-gtid-purged=OFF`, com cliente compatível com o servidor. A alternativa
implementada usa PyMySQL já presente no backend, evitando instalar outro
cliente e garantindo que as contagens/hashes pertençam à mesma transação
das linhas exportadas. A transação é somente leitura, REPEATABLE READ,
WITH CONSISTENT SNAPSHOT, exclusivamente InnoDB. SELECTs mantêm metadata
locks; alterações de estrutura não devem ser agendadas junto do backup.
O esquema é reconferido antes de concluir. Views, triggers, rotinas,
eventos, colunas geradas ou referências entre bases ainda não suportados
causam falha explícita em vez de cópia incompleta silenciosa.
O `sql_mode` da origem é registrado. O CREATE TABLE é obtido em modo
canônico completo: ANSI pode ocultar opções de engine/charset no SHOW
CREATE. Na comparação 8.0/8.4, apenas o contador AUTO_INCREMENT e a
declaração redundante de charset já determinada pela mesma collation são
normalizados; uma collation diferente continua sendo divergência.
Referências: [snapshot MySQL](https://dev.mysql.com/doc/refman/8.4/en/commit.html)
e [limites do mysqldump consistente](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html).

Um diretório `.partial` nunca é restaurável. Só após conferir arquivos e
hashes o manifesto CONCLUIDO é publicado por renomeação. Falha retorna
código 1, gera registro FALHA e preserva o parcial para diagnóstico.

## Backup diário

```powershell
python -m scripts.backup --destino "C:/Users/mathe/OneDrive/Backups-SprintMarrom"
```

O destino fica fora do repositório e dos diretórios de originais, separado
do servidor Aiven. A pasta no OneDrive é local enquanto não sincronizada:
o código não afirma que o upload foi confirmado. Não há retenção/apagamento
automático; acompanhar espaço e manter cópias sincronizadas.

O agendamento instalado é `SprintMarrom-backup-diario`, 02:00 no fuso de
São Paulo. O computador deve estar ligado, com sessão Matheus aberta,
rede e Aiven acessíveis. `StartWhenAvailable` executa uma tarefa perdida
quando possível; não transforma um computador desligado em servidor 24 h.
Logs ficam em `instance/operacao/logs`. Conferir Último Resultado no
Agendador: 0 = sucesso; outro valor = falha. Workbench manual é apenas apoio.

## Restauração isolada, passo a passo

1. Manter um MySQL 8.x local disponível. Não usar Aiven/dev/test como alvo.
2. No `.env` ignorado pelo Git, definir `RESTORE_DATABASE_URL` com usuário
   local capaz de criar uma base e nome **novo**
   `marrom_restore_<identificador>`. Não colocar senha no comando.
3. Escolher um diretório `backup-...` completo e executar:

```powershell
python -m scripts.restaurar --backup "CAMINHO/backup-..." --destino-arquivos "CAMINHO_NOVO/ensaio"
```

4. O comando verifica hashes antes de criar a base; recusa base/diretório
   existentes, cria tabelas e importa as linhas, restaura arquivos e valida
   cada contagem/hash, DDL, revisão Alembic e conexão pela factory Flask.
   Como religar FOREIGN_KEY_CHECKS não valida linhas antigas, faz também
   consultas explícitas para detectar referências órfãs.
5. No Workbench, criar conexão local 127.0.0.1/3306 com o usuário do ensaio;
   atualizar Schemas e abrir a base indicada no relatório. Consultar:

```sql
SHOW TABLES;
SELECT * FROM alembic_version;
SELECT COUNT(*) FROM registros_gps;
SELECT COUNT(*) FROM observacoes_tratadas;
```

6. A evidência completa é `resultado-restauracao.json` no diretório de
   recuperação. Outro integrante reproduz esses passos antes do aceite
   humano exigido no cartão; uma execução do Codex não é essa reprodução.

O ensaio não inicia coletores, não troca DATABASE_URL do site e não
sobrescreve nenhuma base existente. Não há DROP automático, inclusive em
falha; um ambiente parcial fica identificado para diagnóstico.
A revisão Alembic restaurada é a do backup, não uma atualização silenciosa
da origem. Na verificação de 20/11, a Aiven estava em `us29_0012`; o código
da main já contém migrações posteriores. Antes de promover uma recuperação
para esse código, revisar/aplicar `flask --app app db upgrade` no ambiente
isolado e conferir novamente. As bases compartilhadas não são migradas
por este ensaio.

## Retomada e ensaio semestral

Para promover uma recuperação real, conferir o relatório, configurar
DATABASE_URL/CA e os caminhos restaurados de `configuracao.json`, obter
token/senhas do responsável, testar `/health` e consultas, regenerar Parquet
e só então iniciar os workers. Manter a origem desligada para evitar dois
coletores. Usar diretório COLETA_STATE_DIR novo no ambiente recuperado,
pois checkpoint/token de posse antigo não deve contaminar o ensaio.

O comando de ensaio completo seleciona o último backup válido, cria nome
local único e registra início/fim, volume por tabela, hashes e duração:

```powershell
python -m scripts.ensaio_recuperacao --backups "C:/Users/mathe/OneDrive/Backups-SprintMarrom" --destino "C:/Users/mathe/AppData/Local/TimeMarrom/ensaios-restauracao"
```

Meta: até 24 h **para o volume documentado**, sem extrapolar para cinco
anos de dados. A tarefa `SprintMarrom-ensaio-semestral` começa em
**20/05/2027 às 10:00** e repete em maio/novembro, dia 20. Responsável:
Matheus. Exige MySQL local e demais condições acima; não afirma que o
ensaio futuro já ocorreu. Após cada execução, outra pessoa confere o
relatório e registra o aceite. A data no processo inicial é 20/05/2027.

Para recriar os três agendamentos desta máquina:

```powershell
./scripts/agendar_operacao.ps1 -DestinoBackup "C:/Users/mathe/OneDrive/Backups-SprintMarrom" -DestinoEnsaio "C:/Users/mathe/AppData/Local/TimeMarrom/ensaios-restauracao"
```

## Validação

`tests/recuperacao/` verifica corrupção, parciais, tipos e recusa de alvos
compartilhados. A integração opt-in usa somente MySQL local e duas bases
UUID descartáveis. Testa backup sob INSERT concorrente, restauração do
snapshot original, geometria/binário/decimal/TIME/JSON/nulos, arquivo externo,
conexão Flask, FKs e falha de origem corrompida. A evidência de execução
real (quando disponível) é separada desses cenários sintéticos.

## Resultado real de 20/11/2026 — pronto para review

O backup v2 da Aiven (MySQL 8.4.11) foi restaurado no MySQL local 8.0.46
em **40,5 segundos**: 21 tabelas, 170.648 registros GPS, 11.479 observações
tratadas, 96.808 trechos, um ZIP original e o limite municipal. Todos os
hashes/contagens e **27 chaves estrangeiras** conferiram; a aplicação conectou.
Não extrapolar esse tempo para um volume maior que o registrado.

Depois da conferência exata do backup, as migrações da main foram aplicadas
**somente na base isolada** (`us29_0012` → `us05_0014`). Todos os registros
originais continuaram com os mesmos hashes; `flask db check` não encontrou
operações novas e `/health` retornou 200. A reflexão Alembic de LINESTRING
gera aviso; a geometria também foi conferida diretamente pelo DDL e pelos
hashes binários, não apenas pelo autogenerate.

Apenas a base `marrom_restore_20261120_173739_008bfe` foi mantida para inspeção.
As bases locais das tentativas anteriores foram removidas após a recuperação
verificada; pacotes de diagnóstico ficaram separados dos backups selecionáveis.
A Aiven não foi migrada nem teve seus dados alterados por esta tarefa.

**482 testes da suíte + 3 integrações MySQL passaram**, além de 14 subtestes;
9 testes opt-in foram ignorados na suíte comum (as três integrações US32
foram executadas separadamente). Revisão técnica realizada pelo Codex.
Backup diário e ensaio semestral tiveram resultado 0 no Agendador.
O disparo desta validação foi manual, usando as mesmas tarefas cadastradas;
