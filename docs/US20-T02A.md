## Persistência

Reutiliza `ExecucaoProcessamento` / `execucoes_processamento` (migração 0009,
diagrama de classes: "pedido durável de trabalho, versões, chave única,
tentativas e reserva"). **Nenhuma migração nova**: todos os campos já existem.

| Necessidade            | Campo                                                              |
|------------------------|--------------------------------------------------------------------|
| Identificador          | `id` (UUID)                                                        |
| Tipo                   | `tipo = 'RECALCULO_INDICADOR'`                                     |
| Chave lógica única     | `chave_logica` (`UNIQUE uq_execucoes_processamento_chave_logica`)  |
| Estado                 | `estado`: `AGUARDANDO`, `PROCESSANDO`, `PRONTO`, `ERRO` (CHECK existente) |

## Chave lógica

`recalculo-us20:` + SHA-256 de JSON canônico com tipo, indicador, escopo,
início, fim, `versao_base` e `versao_regra`.

- Mesma janela/escopo/indicador e mesmas versões → mesmo pedido, inclusive se o
  pedido vier de outro resultado antigo (outra `versao_calculo` / `versao_conjunto`).
- Nova `versao_regra` ou nova `versao_base` → nova chave e novo pedido.
- `versao_codigo` fica **fora** da chave: um novo deploy não duplica trabalho.
- **Revisão 27/11/2026 — gerações (`chave_da_geracao`).** Antes, um pedido PRONTO
  com a mesma chave era devolvido mesmo quando chegavam dados novos, e a
  atualização desaparecia. Agora: se existe pedido da mesma base ainda por ler
  (AGUARDANDO ou ERRO com tentativas), ele é reutilizado; se todos já leram um
  snapshot igual ou maior, é repetição; senão é criada a geração `base:<snapshot>`.
  Pedidos anteriores e seu histórico ficam intactos. Na publicação, uma geração
  antiga não sobrescreve resultado publicado depois do início da sua leitura.

## Idempotência e concorrência

O `UNIQUE` do banco decide quem vence. A consulta prévia é só uma otimização.
`JobService.solicitar`: se o INSERT violar a chave, ou se o InnoDB abortar por deadlock (1213) ou por
espera de lock (1205), o lote inteiro é desfeito e repetido numa transação nova,
até 3 vezes. Essa transação já enxerga o pedido vencedor. Qualquer outra falha,
como uma FK inválida, desfaz o lote e é propagada.

## Uso

```python
from app.reprocessamento.planos import planejar_regra
from app.reprocessamento.pedidos import registrar_pedidos_do_plano, pedidos_pendentes

plano = planejar_regra(...)                  # US20-T01B
pedidos = registrar_pedidos_do_plano(plano)  # confirma o plano e grava os pedidos
pendentes = pedidos_pendentes()              # após reinício: AGUARDANDO, ERRO, reserva vencida
```

Para dado tardio (`tardios.planejar_dado_tardio`), passe `plano["resultados"]`
a `registrar_pedidos(...)` com `origem` explícita.
